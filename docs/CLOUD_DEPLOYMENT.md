# Развёртывание общего облака Telecom Manager

## Текущее развертывание

Состояние на 2 октября 2026 года: production cloud работает по адресу
`https://telecom.pmguard.ru` на общем VPS, но в отдельной установке
`/opt/telecom-manager-cloud`. Контейнеры, сеть и PostgreSQL volume отделены от
старого сайта. Cloud app опубликован только на `127.0.0.1:8001`, PostgreSQL не
имеет host port, Caddy обслуживает HTTPS на `:443`; проверены health `200` и
редирект HTTP `308`. Регистрация и push/pull синхронизация прошли публичный
smoke-тест, временные организации удалены, база пуста. Цены — 1 490 ₽/месяц и
14 900 ₽/год, проба — 14 дней.

Приём оплаты намеренно выключен: production `YOOMONEY_WALLET`,
`YOOMONEY_NOTIFICATION_SECRET` и `YOOMONEY_FALLBACK_NOTIFICATION_URL` пусты,
потому что общий кошелёк PMGuard использует единственный callback, а его
безопасное переключение и live payment ещё не проверены. Новый независимый
вариант Robokassa добавлен в код, но ещё не развёрнут и не проверен платежом.
PMGuard, его DNS и его кошелёк изменять для приёма оплаты Telecom не требуется.

2026-10-02 закрытая локальная копия облачной базы создана в
`/opt/telecom-manager-cloud/backups/` и восстановлена тестовым скриптом в
одноразовый PostgreSQL без сети, тома и опубликованных портов: миграция
`202610040025`, 25 таблиц. Это подтверждает читаемость архива, но он находится
на том же VPS; ежедневная off-site копия и уведомления об ошибках ещё не
настроены.

> Облако можно развернуть на том же VPS, что и текущий сайт, или на отдельном.
> В обоих случаях используйте отдельные контейнеры и новую PostgreSQL-базу.
> Не меняйте `HOSTING_MODE` текущего рабочего сервера.

В общей облачной версии все клиенты могут работать через один облачный сервис,
но у каждой организации собственные пользователи, записи синхронизации,
платежи и подписка. Сервер выбирает организацию по проверенному токену
устройства; клиент не может прочитать или изменить записи другой организации,
даже если знает её идентификатор записи. Это логическое разделение в общей
базе, а не отдельная физическая база на каждого клиента.

Облачное приложение и PostgreSQL разворачиваются отдельными контейнерами и с
отдельной базой от действующего сайта. Их можно разместить на том же VPS: это
не меняет данные текущей организации. Для клиентов общего облака доступны
мобильное приложение и API синхронизации. Веб-панель пока не разделена по
организациям, поэтому учётные записи облачных клиентов не могут войти в неё.
Для self-hosted версии веб-панель остаётся доступной.

Новая облачная организация создаётся через отдельную регистрацию. Обычный вход
без членства в организации отклоняется и не запускает новый пробный период.

Администратор облачной организации создаёт учётные записи сотрудников в
мобильном приложении: указывает имя, уникальный логин, пароль и роль. Облачную
учётную запись нельзя присоединить к организации другого клиента только по
логину. Приглашение уже существующего пользователя сохраняется для self-hosted
и прежней legacy-организации. Сотрудник входит в приложение по созданным
администратором логину и паролю.

## Что потребуется

- VPS с Docker и Docker Compose (можно использовать текущий сервер, если хватает ресурсов);
- домен, например `cloud.example.ru`, с DNS-записью на VPS;
- HTTPS-прокси (Nginx, Caddy или панель сервера);
- отдельные надёжные пароли PostgreSQL и `APP_SECRET_KEY`;
- отдельный магазин ЮMoney или Robokassa, оформленный на владельца сервиса,
  условия обработки чеков, тарифы и секреты уведомлений.

Для размещения рядом с текущим сайтом задайте облаку отдельный домен или
поддомен. Текущий сайт продолжит слушать свой порт. База облака использует
отдельный закрытый контейнер и том `telecom-manager-cloud-postgres-data`.
Проверьте свободную память VPS перед запуском: облако добавляет ещё приложение
и PostgreSQL.

## Настройки `.env`

Скопируйте `.env.example` в `.env`, затем задайте:

```text
APP_ENV=production
APP_DEBUG=false
APP_SECRET_KEY=случайный-уникальный-ключ-не-короче-32-символов

POSTGRES_DB=telecom_cloud
POSTGRES_USER=telecom_cloud
POSTGRES_PASSWORD=случайный-уникальный-пароль-не-короче-24-символов

HOSTING_MODE=cloud
CLOUD_TRIAL_DAYS=14
CLOUD_DOMAIN=cloud.example.ru
# Only on the first migration of this new, empty cloud database.
BOOTSTRAP_CLEAN_DEMO_PROVIDER_CATALOG=true
BOOTSTRAP_CLEAN_CLOUD_DEFAULTS=true
# Recommended launch prices: 1,490 ₽/month or 14,900 ₽/year (two months free).
CLOUD_MONTHLY_PRICE=1490
CLOUD_YEARLY_PRICE=14900
CLOUD_PAYMENT_LINK_MINUTES=60
CLOUD_PAYMENT_PROVIDER=yoomoney
MOBILE_LOGIN_RATE_LIMIT=30
MOBILE_LOGIN_RATE_WINDOW_SECONDS=900
CLOUD_REGISTRATION_RATE_LIMIT=5
CLOUD_REGISTRATION_RATE_WINDOW_SECONDS=86400
YOOMONEY_WALLET=
YOOMONEY_NOTIFICATION_SECRET=
YOOMONEY_FALLBACK_NOTIFICATION_URL=
YOOMONEY_FALLBACK_LABEL_PREFIXES=
ROBOKASSA_MERCHANT_LOGIN=
ROBOKASSA_PASSWORD1=
ROBOKASSA_PASSWORD2=
ANDROID_RELEASE_TAG=android-v1.1.1
```

Для независимого магазина Robokassa укажите `CLOUD_PAYMENT_PROVIDER=robokassa`,
логин магазина и технические пароли №1 и №2 из отдельного кабинета Telecom.
Настройте в Robokassa `ResultURL` как
`https://telecom.pmguard.ru/api/billing/robokassa/result` и метод POST. Должны
совпадать алгоритм подписи MD5, основной пароль №1/№2 и валюта/сумма; сначала
проверьте тестовый платёж в тестовом кабинете, затем — отдельный реальный платёж.
Если работаете как самозанятый, отдельно активируйте Робочеки СМЗ и проверьте
поступление чека в «Мой налог»: платёжный callback сам по себе не создаёт чек НПД.
Регулярные автосписания у Robokassa доступны только после согласования с ними;
в текущей версии клиент сам продлевает доступ разовым платежом.

Для ЮMoney оставьте `CLOUD_PAYMENT_PROVIDER=yoomoney` и настройте отдельный
кошелёк/магазин Telecom с собственным callback. Не используйте общий кошелёк
PMGuard и не меняйте его callback. Переменные `YOOMONEY_FALLBACK_*` относятся
к прежней необязательной маршрутизации, по умолчанию она отключена; не задавайте
для неё адрес PMGuard. Оплата Telecom скрыта, пока обязательные реквизиты
выбранного независимого провайдера не заданы.

Сразу после первой успешной миграции верните
`BOOTSTRAP_CLEAN_CLOUD_DEFAULTS=false` или удалите эту строку из `.env`.
При включённом флаге миграция удаляет только неизменённую начальную запись
`admin` с демо-паролем, только если база действительно облачная, в ней нет
организаций и действий пользователя. Это освобождает логин `admin` для первой
регистрации владельца. Для существующей базы этот флаг не включайте.

Стартовые цены в примере — 1 490 ₽/мес. или 14 900 ₽/год; их можно изменить в
production `.env` до запуска. Годовой тариф дешевле помесячной оплаты на 2 980 ₽
(16,7%, эквивалент двух месяцев). Цены можно поменять перед запуском. Если хотя бы
одна цена равна нулю, соответствующий тариф выключен. Для включения оплаты также
задайте секреты выбранного провайдера и все обязательные адреса уведомлений.
Без них кнопка оплаты не появится, а создание платёжной ссылки будет отклонено.
Для ЮMoney настройте отдельный кошелёк Telecom; дополнительная пересылка
уведомлений по умолчанию выключена. Оплата скрыта, если сервер не сможет
подтвердить платёж. Значение `CLOUD_MONTHLY_PRICE` и `CLOUD_YEARLY_PRICE` — сумма,
списываемая с клиента; комиссия зависит от тарифа Robokassa/ЮMoney. Текущие
условия уточняйте у выбранного провайдера. ЮMoney удерживает комиссию из
поступления на кошелёк. Текущие формулы комиссии приведены в
[документации формы ЮMoney](https://yoomoney.ru/docs/payment-buttons/using-api/forms).
`CLOUD_DOMAIN` указывается как DNS-имя без схемы и пути; production отвергает
примерное имя из шаблона. Приложение использует этот домен для канонических
HTTPS-ссылок оплаты, а не доверяет `Host` из запроса.
Облачный Compose принудительно устанавливает `HOSTING_MODE=cloud`, выключает
debug и подключает приложение к собственной БД по адресу `postgres`. При
`APP_ENV=production` приложение не запустится с шаблонным ключом или паролем
короче указанного минимума. Профиль также принудительно включает флаг `Secure`
для веб-cookie: браузер отправляет сессионную cookie только по HTTPS.

## Первый запуск

```bash
git clone https://github.com/magomedov1009/telecom-manager.git /opt/telecom-manager-cloud
cd /opt/telecom-manager-cloud
cp .env.example .env
# заполните .env
```

Для первой установки безопаснее запустить PostgreSQL и применить миграции до
первого запуска приложения:

```bash
docker compose -f docker-compose.cloud.yml build app
docker compose -f docker-compose.cloud.yml up -d postgres
docker compose -f docker-compose.cloud.yml run --rm app alembic upgrade head
docker compose -f docker-compose.cloud.yml up -d app
```

Для облака используйте только `docker-compose.cloud.yml`: он запускает приложение
без режима перезагрузки исходников, не публикует PostgreSQL в интернет и
открывает порт приложения только на `127.0.0.1:8001`. Его отдельная Docker-сеть
не совпадает с сетью текущего сайта. В приложение указывается адрес
`https://cloud.example.ru` без `/login` и `/api/mobile`.
Процесс приложения в контейнере работает от отдельного непривилегированного
пользователя. Uvicorn учитывает HTTPS-заголовки reverse proxy, поскольку
облачный порт доступен снаружи только через прокси или локальный интерфейс VPS;
не публикуйте порт `8001` во внешнюю сеть напрямую.
Проверка контейнера обращается к `/health/ready`: она возвращает готовность
только после успешного запроса к PostgreSQL; `/health/live` проверяет только
работу процесса приложения.

Если на VPS ещё нет reverse proxy, в Compose подготовлен дополнительный Caddy
профиль. Перед запуском замените `CLOUD_DOMAIN` в `.env`, направьте DNS-запись
поддомена на VPS и убедитесь, что входящие порты 80/443 доступны, а локально их
не занимает текущая служба. Текущий сайт на `:8000` не перенастраивается. Затем
после первоначального запуска БД, миграций и приложения включите только
прокси-профиль:

```bash
docker compose -f docker-compose.cloud.yml --profile https-proxy config
docker compose -f docker-compose.cloud.yml --profile https-proxy up -d https_proxy
```

Caddy получает отдельную сеть с облачным приложением; контейнер PostgreSQL в эту
сеть не подключён. Прокси автоматически получает HTTPS-сертификат для домена.
Профиль публикует порты 80/443 на всех интерфейсах VPS, поэтому не запускайте
его, пока не подтвердили доступность DNS, правила firewall и отсутствие другого
слушателя на этих портах. Если там уже работает Nginx/Caddy, не запускайте этот
профиль: добавьте отдельный virtual host в существующую конфигурацию и направьте
его на `127.0.0.1:8001`.

Если текущий сайт уже обслуживается Caddy или Nginx, не заменяйте его
конфигурацию целиком: добавьте отдельный виртуальный хост для нового поддомена
рядом с существующим блоком. Это сохранит текущий сайт на месте и направит
только облачный поддомен на новый контейнер. Например, для Caddy добавьте в
существующий `/etc/caddy/Caddyfile` отдельный блок, заменив домен:

```text
cloud.example.ru {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8001
}
```

Для Nginx создайте отдельный `server`-блок для поддомена (не меняя блок
текущего сайта) и проксируйте его на `http://127.0.0.1:8001`, передавая
`Host`, `X-Real-IP`, `X-Forwarded-For` и `X-Forwarded-Proto`. Настройте TLS
для нового имени через уже используемый на VPS механизм выпуска сертификатов.
Перед перезагрузкой Nginx проверяйте конфигурацию командой `nginx -t`; затем
перезагружайте только reverse proxy. Если на VPS нет домена/поддомена, DNS,
свободного HTTPS-виртуального хоста или доступа к конфигурации прокси, сначала
решите это с администратором сервера, не останавливая работающий сайт.

DNS домена должен указывать на VPS, а входящие порты 80 и 443 должны быть
доступны для выбранного reverse proxy. После настройки HTTPS проверьте страницы `/privacy-policy` и
`/account-deletion` перед публикацией приложения.

## Отдельная оплата Telecom

Не меняйте платёжные настройки, callback, DNS или сервисы PMGuard. Для YooMoney
создайте отдельный кошелёк/магазин Telecom и задайте в его настройках только
этот адрес уведомлений:

```text
https://cloud.example.ru/api/billing/yoomoney/notification
```

Секрет отдельного магазина Telecom заносится исключительно в
`YOOMONEY_NOTIFICATION_SECRET` на сервере. В GitHub, APK и чат его не
отправляют. `YOOMONEY_FALLBACK_*` оставьте пустыми. После настройки собственного
магазина и проверки тестовым платежом можно перезапустить только cloud app:

```bash
docker compose -f docker-compose.cloud.yml up -d --build app
```

Для каждого выпуска Android задайте в серверном `.env` переменную
`ANDROID_RELEASE_TAG` с опубликованным тегом (например, `android-v1.1.2`) и
перезапустите контейнер приложения. Так сервер продолжит сообщать об обновлении
установленным версиям; новые версии приложения дополнительно автоматически
сверяют этот адрес с GitHub Releases.

## Резервные копии

В репозитории есть `scripts/backup-cloud.sh`: он делает custom-format архив и
проверяет его командой `pg_restore --list`. Если задан `RCLONE_REMOTE_DIR`,
скрипт отправляет архив через настроенный `rclone` во внешнее хранилище и
сверяет копию; при ошибке загрузки/сверки локальная копия сохраняется. Если
внешнее хранилище не задано, скрипт создаёт и сохраняет только локальную копию
и явно сообщает, что она не off-site. Старые локальные архивы удаляются после
успешной проверки нового архива (и внешней сверки, если remote включён); срок
задаётся через `LOCAL_BACKUP_RETENTION_DAYS` (1–3650 дней). Удаляются только
обычные файлы `cloud-backup-*.dump` непосредственно в `backups/`. Во внешнем
хранилище срок хранения настраивается отдельно. Каталог `backups/` закрыт для
Git и Docker build context.

Для локального ежедневного расписания в репозитории есть systemd service/timer
с 30-дневным сроком хранения. На Telecom VPS установите их и выполните первую
копию вручную:

```bash
cd /opt/telecom-manager-cloud
install -m 0644 deploy/systemd/telecom-manager-cloud-backup.service /etc/systemd/system/
install -m 0644 deploy/systemd/telecom-manager-cloud-backup.timer /etc/systemd/system/
systemctl daemon-reload
bash scripts/backup-cloud.sh
systemctl enable --now telecom-manager-cloud-backup.timer
systemctl start telecom-manager-cloud-backup.service
systemctl status telecom-manager-cloud-backup.timer
```

Чтобы дополнительно включить off-site копию, настройте `rclone` от имени того же
системного пользователя и сначала проверьте загрузку вручную:

```bash
cd /opt/telecom-manager-cloud
RCLONE_REMOTE_DIR='remote-name:telecom-manager-cloud' bash scripts/backup-cloud.sh
```

Для `rclone` запускайте тот же сервис с защищённой конфигурацией remote; не
помещайте токены в crontab. Настройте оповещение по ненулевому коду выполнения
задания и правила хранения внешнего хранилища. Успешный `rclone check`
подтверждает совпадение копии, но не заменяет тестовое восстановление.

Периодически проверяйте архив командой:

```bash
bash scripts/restore-test-cloud.sh /path/to/cloud-backup.dump
```

Сценарий создаёт отдельный одноразовый PostgreSQL-контейнер без сети, портов и
тома, восстанавливает туда архив, проверяет таблицы и версию Alembic, после чего
удаляет только созданный им контейнер. Рабочая облачная база и её том не
используются и не изменяются. При необходимости можно задать образ через
`POSTGRES_RESTORE_TEST_IMAGE`; по умолчанию применяется `postgres:16-alpine`.
Для аварийного восстановления в рабочую систему используйте отдельную процедуру
ниже — этот тестовый сценарий никогда не направляет восстановление в неё.
Подписка заканчивается без удаления данных, но резервные копии всё равно
обязательны.

## Обновление

Перед каждым обновлением сначала создайте архив, проверьте его через
`scripts/backup-cloud.sh` и проверьте, что он завершился успешно, включая
внешнюю сверку. Затем обновите исходники
и соберите образ, остановите приложение, примените миграции новым образом и
только после успеха запустите приложение снова:

```bash
cd /opt/telecom-manager-cloud
bash scripts/backup-cloud.sh
git pull --ff-only origin main
docker compose -f docker-compose.cloud.yml build app
docker compose -f docker-compose.cloud.yml stop app
docker compose -f docker-compose.cloud.yml run --rm app alembic upgrade head
docker compose -f docker-compose.cloud.yml up -d app
```

Если миграция завершилась ошибкой, оставьте приложение остановленным и не
запускайте новый код на неизвестной версии схемы. Сохраните текст ошибки;
перед восстановлением проверьте архив и восстанавливайте его только в отдельную
пустую базу.
