# Коммерческий запуск Telecom Manager

Состояние на 2 октября 2026 года. Коммерческий код находится в PR #16
(`commercial-cloud-launch`), CI успешно завершился, но PR пока открыт и не слит;
общее облако и приём платежей ещё не запущены. Для облака выбран тот же VPS, что
и для текущего сайта, и домен `telecom.pmguard.ru`, уже указывающий на него.
Telecom Manager и текущий сайт остаются раздельными контейнерами и базами;
организации общего облака логически изолированы друг от друга в отдельной базе.
Для ЮMoney предполагается общий кошелёк PMGuard с маршрутизацией единственного
callback по меткам платежа; реальные реквизиты и маршруты пока не настроены.

Локальная проверка 2 октября 2026 года: `92 passed, 50 subtests passed`,
единственная Alembic head `202610040025`, offline SQL от пустой базы сгенерирован,
Android: 43 теста и `flutter analyze` прошли на Flutter 3.44.7; создана локальная
проверочная AAB-сборка `mobile/build/app/outputs/bundle/release/app-release.aab`.
Сертификат проверен: `CN=Android Debug`, значит этот файл не предназначен для
Google Play и не является релизом для пользователей. Проверены создание внешней
ссылки оплаты, раздельные операции списания и сохранение локальной очереди после
отказа синхронизации с кодом 402 до возобновления подписки. Контейнерная
сборка и реальный PostgreSQL здесь недоступны: Docker/Podman и локальный сервер
PostgreSQL не установлены. YAML Compose статически разобран; проверено, что app
ports `8000`/`8001`/`8002`, имена контейнеров, приватная сеть БД и тома данных не
совпадают между legacy, cloud и self-hosted; в трёх профилях PostgreSQL не
публикуется на хосте, а cloud база не подключена к сети HTTPS-прокси. VPS и
кошелёк ЮMoney этой проверкой не изменялись; read-only состояние VPS проверено
отдельно ниже. GitHub Actions workflow
использует отдельную PostgreSQL 16 для миграций и также создаёт и восстанавливает
CI-архив в изолированном контейнере; CI включает явные флаги очистки только
для отдельной пустой облачной базы, чтобы проверять путь первой установки.
Отдельная Flutter job на закреплённом SDK
запускает анализ, мобильные тесты и проверочную сборку AAB без публикации и без
Play-ключа. Оба запуска GitHub Actions для коммита `b8fa3d7` завершились успешно:
backend и mobile (включая AAB). Это проверка CI, а не публикация приложения или
слияние PR в `main`.

## Реализовано

### Текущая организация и режимы сервера

- [x] Все организации, существовавшие до коммерческой миграции, отмечаются
  legacy; их синхронизация не ограничена подпиской. Миграционный тест проверяет
  несколько существующих организаций, а ASGI-тест выполняет реальный push/pull
  legacy-организации даже при `HOSTING_MODE=cloud` и подтверждает, что подписка
  ей не создаётся. Self-hosted сервер работает без оплаты.
- [x] Новая облачная регистрация получает отдельную организацию и пробный период
  один раз на аккаунт владельца; каждая следующая организация создаётся без
  синхронизации до оплаты. Признак хранится на аккаунте и не сбрасывается при
  удалении отдельной организации.
- [x] Вход cloud-аккаунта без членства отклоняется, чтобы удалённый сотрудник
  не мог начать новый пробный период простым входом.
- [x] Синхронизация облака проверяет активность подписки; при окончании данные
  сохраняются, а синхронизация приостанавливается.
- [x] Облачные организации изолированы от таблиц legacy-веб-сайта. Доступ к
  общей веб-панели закрыт для cloud-only аккаунтов, пока в ней нет фильтрации
  по организациям.
- [x] Администратор облачной организации может создавать аккаунты сотрудников
  с отдельными логинами и ролями прямо в приложении; подключить чужую учётную
  запись только по логину нельзя.
- [x] Подготовлен отдельный Docker Compose для облака: порт `127.0.0.1:8001`,
  отдельные контейнеры и том PostgreSQL. Приложение ждёт готовой PostgreSQL,
  а HTTPS-прокси — проверки `/health/ready`; это закреплено Compose-тестом.
  Облако можно запустить рядом с текущим сайтом на порту `8000`.
- [x] Добавлен необязательный Caddy HTTPS-профиль: отдельная сеть соединяет
  прокси только с cloud app, PostgreSQL в неё не подключён; стандартные порты
  80/443 публикуются только при явном запуске профиля. Текущий сайт на `:8000`
  не перенастраивается.
- [x] Для самостоятельной установки клиента добавлен production Compose с
  отдельной сетью/томом, закрытой БД и портом приложения `127.0.0.1:8002`;
  существующий dev Compose оставлен без изменений.
- [x] Новые production Compose требуют production-режим и отклоняют шаблонные
  или короткие секреты; старый Compose текущего сайта остаётся совместимым.
- [x] Цепочка Alembic имеет единственную актуальную head-ревизию; offline SQL
  от пустой базы генерируется без ошибок; применение на чистом PostgreSQL и
  восстановление из backup ещё нужно проверить на VPS.
- [x] Новое мобильное пространство предлагает создать собственные провайдера и
  склад; новая серверная установка безопасно очищает только неизменённые
  demo-пары на полностью пустой базе. Существующие организации и операции
  миграция сохраняет; отдельные тесты проверяют пустую базу, существующую
  организацию, операции и изменённый каталог. На первой облачной установке с
  отдельным одноразовым флагом удаляется и недоступная демо-учётная запись
  `admin`; миграция требует cloud-режим, пустые таблицы организаций и операций,
  единственного незатронутого администратора с исходным хешем. Существующие
  либо изменённые учётные записи сохраняются; тесты покрывают эти ограничения,
  а HTTP-регистрация первой организации проверяет, что логин `admin` свободен.
- [x] Облачный сервис рассчитан на несколько организаций в одном приложении и
  одной базе: мобильные записи, журнал изменений, платежи и подписки привязаны
  к `organization_id`; синхронизация ограничена выбранной организацией. Текущий
  рабочий сайт остаётся в отдельном контейнере и отдельной базе.
- [x] Docker-сборка исключает `.env`/`.env.*` с сохранением безопасного
  `.env.example`, Git-историю, базы, локальные тесты, mobile tree и `artifacts/`;
  локальные ключи/хранилища Android и тестовый APK также исключены из Git.
  Шаблоны для `.jks`, `.keystore`, `.p12`, `.pfx`, `.pem` и `.key` исключены
  одновременно из Git и Docker build context.

### Подписки и ЮMoney

- [x] Утверждены стартовые облачные тарифы: 1 490 ₽/мес. или 14 900 ₽/год
  (экономия 2 980 ₽, или 16,7%, при оплате за год); пробный период — 14 дней.
  Значения по умолчанию внесены в `.env.example` и инструкцию развёртывания;
  рабочая конфигурация сервера при этом не менялась.
- [x] Для самостоятельного сервера согласована стартовая услуга установки за
  19 900 ₽ и необязательная поддержка/обновления за 6 900 ₽ в год; VPS клиент
  оплачивает отдельно. Это цены услуги, а не установленная лицензия на ПО.
  До продажи такой установки требуется утвердить условия лицензии/использования:
  в публичном репозитории проекта сейчас нет файла `LICENSE`.
- [x] Настраиваемые месячный и годовой тарифы, пробный срок, статус и дата
  окончания.
- [x] Внешняя страница оплаты с уникальной меткой заказа; сумма фиксируется в
  заказе и не меняется для уже открытой ссылки при обновлении тарифных цен.
- [x] Checkout и ссылка возврата строятся на настроенном `CLOUD_DOMAIN`, а не
  на переданном клиентом HTTP `Host`; production отклоняет домен-шаблон.
- [x] Страница checkout запрещает кэширование и передачу `Referer` внешней
  форме платежа; заголовки проверяются тестом.
- [x] Оплата скрыта и новые/уже созданные ссылки блокируются, если отсутствует
  секрет уведомлений и сервер не сможет подтвердить поступление денег.
- [x] При включённых префиксах пересылки checkout остаётся закрытым, пока не
  задан callback связанного сервиса (например, PMGuard).
- [x] Подпись, валюта и сумма уведомления проверяются; повторное уведомление
  не продлевает доступ второй раз. Алгоритм подписи дополнительно сверяется
  независимым тестом с официальным примером ЮMoney.
- [x] Входящий callback ограничен 16 КиБ и 64 полями также при отсутствии
  `Content-Length`; неподдерживаемый тип содержимого отклоняется до обработки.
- [x] Каждая отдельная операция списания сохраняется отдельной квитанцией:
  повтор той же операции идемпотентен, а второе реальное списание по одной форме
  засчитывается как дополнительный оплаченный период и показывается в истории.
  Миграция заполняет квитанции для ранее подтверждённых платежей.
- [x] Если подписанное уведомление повторно использует ID операции с другой
  меткой заказа, доступ повторно не начисляется; событие записывается в журнал,
  а callback подтверждается, чтобы YooMoney не повторяла его бесконечно.
- [x] Ссылки на оплату истекают; новая ссылка отключает страницу прежнего
  ожидающего checkout. Подписанная задержанная квитанция всё равно учитывается.
- [x] В коде подготовлена маршрутизация подписанных уведомлений в PMGuard только
  по меткам `tg_`; уведомление пересылается как
  `application/x-www-form-urlencoded`, без следования HTTP redirects; URL PMGuard
  и ответ JSON `success: true` с HTTP 201 подтверждены по его
  deployment-документации и исходникам. Ответ ограничен 4 КиБ, чтобы связанный
  endpoint не мог заставить сервис читать неограниченное тело.
- [ ] Не проверены доступность live endpoint PMGuard, тестовый платёж и повторы
  уведомления с реальным кошельком. До успешной проверки нельзя переключать
  единственный callback ЮMoney.
- [x] В Android-версии 1.1.1 администратор видит историю до 50 платежей;
  статус обновляется после возврата из браузера.
- [ ] Фискальные чеки не формируются. Текущий checkout использует форму перевода
  на кошелёк ЮMoney; это не подключение магазина и не интеграция с кассой.
  ЮMoney описывает приём платежей на кошелёк физлица и подключение магазина как
  разные сценарии; для магазина предусмотрены заявка, документы, договор и
  техническая интеграция. До платного запуска определить продавца и налоговый
  режим с бухгалтером, уточнить допустимый тип кошелька/договора и применимость
  ККТ либо исключений. Если ККТ требуется, выбрать кассового провайдера,
  подключить отправку электронных чеков и собирать контакт покупателя до оплаты.
  Уведомление ЮMoney о переводе не заменяет фискальный чек. Для интернет-расчётов
  ФНС указывает реквизит «признак расчёта в Интернет» и адрес сайта в электронном
  чеке; проверьте требования с бухгалтером перед запуском:
  [подключение магазина в ЮMoney](https://yoomoney.ru/document/kak-podklyuchit-magazin-k-yoomoney),
  [требования ФНС к чекам при онлайн-оплате](https://www.nalog.gov.ru/rn02/news/activities_fts/16550926/).
- [ ] Утвердить срок хранения платёжной истории при удалении облачного аккаунта.
  Сейчас удаление организации каскадно удаляет `cloud_payments` и подписку вместе
  с рабочими данными. До коммерческого запуска определить с бухгалтером и
  ответственным за персональные данные, какие сведения о транзакциях требуется
  сохранить, обезличить или удалить, затем реализовать и протестировать выбранный
  порядок. Не обещать полное удаление без оговорок, пока это не согласовано.

## Осталось до запуска общего облака

- [x] Пробный период выдаётся один раз на аккаунт владельца; миграция помечает
  владельцев существующих облачных организаций как уже использовавших пробу.
  Новую организацию можно создать, а синхронизацию включить после оплаты.
  Регистрация не подтверждает телефон или email, поэтому создание отдельного
  аккаунта остаётся способом начать пробу заново; блокировка повторной
  регистрации одного человека потребует подтверждённого идентификатора.
- [x] Автоматизированный ASGI-тест проходит регистрацию двух организаций и
  HTTP-запросы синхронизации с разными токенами: одинаковый ID записи не
  раскрывается и не перезаписывается между организациями. Проверка на реальной
  PostgreSQL остаётся частью пробного развёртывания на VPS.
- [x] Вход и облачная регистрация ограничены общими для процессов счётчиками в
  PostgreSQL: до 30 запросов входа за 15 минут и 5 регистраций в сутки с одного
  клиентского IP. IP не хранится открытым текстом. Счётчики удаляются только
  после настроенного окна с дополнительным запасом в сутки, поэтому долгое
  окно регистрации не сбрасывается преждевременно. Пределы и окна настраиваются
  через `.env`; превышение, сброс и длинное окно проверяются тестами.
  Перед запуском проверьте настройки за NAT и у доверенного reverse proxy.

## Защита текущей организации

- Не менять `HOSTING_MODE` работающего self-hosted сервера на `cloud`.
- Облако всегда запускается с отдельным контейнером PostgreSQL и отдельным томом.
- Перед обновлением действующего сайта делать резервную копию его базы.
- Секреты не добавлять в GitHub, APK или чат; хранить только в `.env` сервера.
- Организации общего облака логически изолированы в общей базе. Для усиленной
  защиты серверные запросы должны получать организацию только из проверенного
  токена, а не из произвольного `organization_id` в запросе пользователя.
